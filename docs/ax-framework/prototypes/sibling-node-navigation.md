# 프로토타입: 고밀도 트리 탐색

> 상태: 검토 가능

형제와 하위 노드가 많은 동일한 fixture에서 A+B 결정안과 C 탐색 트랙을 직접 비교한다.

노드 형태와 글자, 연결선, 캔버스는 제품의 현재 `Neutral` 또는 `Soft` 디자인 테마를 그대로 따라간다. 프로토타입 전용 시각 스타일이 가독성 판단에 영향을 주지 않게 하기 위한 것이다.

## 접근 방법

개발 서버를 실행하고 다음 주소를 연다.

```text
http://localhost:3000/dev/ax-tree-navigation-lab
```

개발 환경에서만 접근할 수 있으며 production에서는 404를 반환한다.

## A+B 결정안

목적은 `전체 구조`와 `읽기 보기`의 차이가 설명 없이도 이해되는지 확인하는 것이다.

1. `전체 구조`에서 트리의 범위와 밀도를 확인한다.
2. 관심 있는 가지 노드를 선택한다.
3. `읽기 보기`를 눌러 선택한 가지를 넓어진 좌측 상단 패딩에서 읽는다.
4. 다시 `전체 구조`로 돌아간다.

읽기 보기는 최소 78% 배율과 `세로 4개 × 깊이 3단계`를 기준으로 한다. 최소 슬롯을 만족하는 범위에서 최대 100%까지 가장 크게 확대한다. 하단에는 적용 배율과 현재 캔버스에서 완전히 들어오는 `세로 행 수 × 가로 깊이 수`가 표시된다. 포커스 노드에서 오른쪽과 아래쪽으로 해당 용량만큼 탐색하고, 범위를 벗어난 구조는 pan으로 이어서 확인한다.

fixture의 노드는 픽셀 좌표를 직접 소유하지 않고 `depth × breadth` 위상 좌표를 현재 가로 전개 화면에 투영한다. 읽기 창도 포커스 위상 좌표와 계산된 슬롯 수를 함께 반환하지만, 이 좌표는 서비스 로직용이므로 화면에는 별도로 표시하지 않는다.

확인 질문:

- 두 버튼의 이름으로 결과를 예상할 수 있는가?
- 전체 구조에서 읽기 보기로 전환할 때 선택한 위치를 잃지 않는가?
- 좌측 상단의 포커스 기준점이 가로 전개 방향과 잘 맞는가?
- 표시된 행 수와 깊이 수가 실제로 읽을 수 있는 범위와 일치하는가?
- 읽기 보기에서 화면 밖에 더 많은 구조가 있다는 사실을 알 수 있는가?
- 자동으로 선택된 배율이 충분히 크면서도 최소 슬롯을 보존하는가?
- 넓어진 패딩이 트리와 캔버스 경계를 자연스럽게 분리하는가?

## C 탐색 트랙

목적은 조망과 포커스를 오가는 과정에서 재사용할 가치가 있는 고급 상호작용을 찾는 것이다.

1. 전체 구조에서 관심 있는 가지를 선택한다.
2. 선택한 가지와 하위 노드가 확대되는 과정을 확인한다.
3. breadcrumb와 이전·다음 형제 버튼으로 다른 가지를 탐색한다.
4. `전체 구조`를 눌러 조망 상태로 돌아간다.

확인 질문:

- 축소된 전체 구조에서도 관심 영역을 선택할 수 있는가?
- 주변 영역을 흐리게 남긴 것이 위치 맥락을 유지하는 데 도움이 되는가?
- breadcrumb와 형제 이동 중 어떤 요소가 실제로 유용한가?
- 자동 카메라 이동이 자연스러운가, 통제권을 빼앗는 느낌을 주는가?
- 전체 구조로 돌아왔을 때 방금 보던 가지를 다시 찾을 수 있는가?

## 범위와 중단 조건

이 프로토타입은 제품 UI가 아니며 다음을 결정하지 않는다.

- 최종 버튼 이름과 아이콘
- 확정된 최소 가독 배율
- 키보드 탐색과 스크린 리더 동작
- 실제 패널과 플레이어를 포함한 카메라 영역
- 카메라 상태의 저장과 복원

C에서 위치 감각 개선이나 탐색 효율의 징후가 없다면 기능을 더 추가하지 않고 탐색을 중단한다. 가치가 확인되면 유용했던 상호작용만 별도 후보로 분리한다.
