# 사례: 형제 노드가 많을 때 글자가 지나치게 작아짐

> 상태: 5단계 최종 결정 — 동작 계약 검토

이 문서는 프레임워크를 검증하기 위한 첫 사례다. 아직 제품 해결책을 확정하지 않으며, 사용자 피드백과 현재 구현을 바탕으로 문제의 경계를 정리한다.

## 사용자 피드백

> 형제 노드가 너무 많은 상황에서 화면에 형제 노드를 모두 잡아주느라 폰트가 과도하게 작아진다.

## 1. 문제 정제

### 원래 표현과 실제 동작의 차이

사용자는 글자가 작아진다고 느끼지만 CSS의 글자 크기 자체가 동적으로 바뀌는 것은 아니다. 제품은 노드와 글자를 포함한 캔버스 전체의 카메라 배율을 낮춘다.

현재 테마의 노드 글자는 `Neutral` 13px, `Soft` 14px다. 카메라는 전체 트리를 맞출 때 최저 0.3배까지 축소할 수 있으므로 화면상 글자 크기는 각각 약 3.9px, 4.2px까지 내려간다. 168×60px 노드도 약 50×18px로 보인다.

### 확인된 구현 사실

- 노드는 내용과 관계없이 168×60px로 고정된다.
- 형제 노드는 세로로 쌓이며 노드 사이에 32px 간격을 둔다.
- 자식 서브트리가 있으면 다음 형제는 앞선 형제의 서브트리 전체가 끝난 뒤에 놓인다.
- 전체 맞춤은 패널과 플레이어가 가리지 않는 영역에서 사방 24px 여백을 제외한 공간을 기준으로 배율을 계산한다.
- 전체 맞춤의 최대 배율은 1, 최소 배율은 0.3이다.
- 접어서 보이지 않는 노드와 그 연결선은 맞춤 대상에서 제외된다.
- 구조가 바뀔 때마다 자동으로 전체 맞춤을 다시 하지는 않는다.

단순히 자식이 없는 형제 `n`개만 세로로 쌓인 경우 그 영역의 높이는 대략 다음과 같다.

```text
높이 = 60n + 32(n - 1)
     = 92n - 32px
```

각 형제에게 하위 트리가 있으면 실제 높이는 이보다 커진다. 맞춤 배율은 사용 가능한 화면 높이를 이 영역의 높이로 나눈 값에 가까우므로, 노드 수뿐 아니라 화면 높이와 펼쳐진 하위 트리의 크기도 문제에 영향을 준다.

### 전체 맞춤이 실행되는 시점

| 시점                       | 사용자 의도 또는 시스템 동작              |
| -------------------------- | ----------------------------------------- |
| 트리를 처음 열었을 때      | 첫 배치 뒤 한 번 자동 실행                |
| 도구 막대의 전체 맞춤      | 사용자가 명시적으로 요청                  |
| 레벨 단위 접기·펼치기      | 구조가 크게 달라져 다음 배치 뒤 자동 실행 |
| 강의 화면 초기화·접힘 복구 | 강의 흐름에서 전체 구조를 다시 표시       |

따라서 현재 확인된 문제는 모든 편집 과정에서 계속 글자가 작아지는 현상이 아니라, **세로로 큰 트리에 전체 맞춤이 적용될 때 구조 전체 표시를 우선해 읽기 어려운 배율까지 축소되는 현상**이다.

### 현재 문제 프레임

> 펼쳐진 형제 또는 형제 서브트리가 시각 프레임보다 큰 상황에서 전체 맞춤을 실행하면, 시스템이 전체 구조를 동시에 표시하기 위해 배율을 최저 0.3까지 낮춘다. 그 결과 사용자는 노드의 존재와 전체 형태는 볼 수 있지만 제목을 읽고 개별 노드를 구별하기 어렵다.

이 문제 프레임은 아직 “글자를 키운다”나 “일부 노드를 숨긴다” 같은 해법을 전제하지 않는다.

### 아직 확인하지 못한 사용자 맥락

- 사용자는 전체 맞춤 후 전체 구조를 훑으려는가, 특정 노드의 제목을 읽으려는가?
- 불만은 최초 진입, 전체 맞춤 버튼, 레벨 펼치기 중 어느 경로에서 가장 자주 발생하는가?
- 전체 구조가 화면 밖으로 나가는 것과 제목을 읽지 못하는 것 중 어느 쪽이 더 큰 실패인가?
- 허용 가능한 최소 가독성을 글자 크기, 노드 식별 가능성, 조작 가능성 중 무엇으로 판단할 것인가?
- 현재의 접기 기능만으로 사용자가 스스로 문제를 해소할 수 있는가? 가능하더라도 그 방법을 쉽게 발견할 수 있는가?

### 성공 조건의 초기 가설

- 전체 구조를 확인하려는 동작과 노드 내용을 읽으려는 동작이 서로를 불필요하게 방해하지 않는다.
- 전체 맞춤 뒤에도 사용자가 다음 탐색 행동을 쉽게 선택할 수 있다.
- 형제가 많다는 이유만으로 제목 읽기와 노드 조작이 사실상 불가능한 상태에 머물지 않는다.
- 해결책이 사용자의 현재 위치와 트리 구조에 대한 인지를 갑자기 잃게 하지 않는다.

수치 기준과 우선순위는 사용자 맥락을 확인한 뒤 정한다.

## 다음 결정 게이트

### 확인된 방향

전체 구조를 조망하는 경험과 제목을 읽으며 탐색하는 경험을 모두 제공한다. 한쪽을 없애 다른 쪽의 문제를 해결하지 않는다.

아직 확정하지 않은 것은 두 의도를 하나의 동작에서 절충할지, 서로 다른 동작이나 화면으로 분리할지다.

## 2. 대응 후보

아래 후보는 버튼 모양이나 문구가 아니라 두 탐색 의도를 연결하는 방식이 서로 다르다. 세부 UI는 후보를 선택한 뒤 프로토타입에서 정한다.

### 후보 A. 하나의 맞춤 동작에 가독성 하한 적용

전체 맞춤이 일정 배율 아래로 내려가지 않게 한다. 한 화면을 벗어난 영역은 이동해서 탐색한다.

- 기대 효과: 현재 경험을 거의 유지하면서 글자가 지나치게 작아지는 상황을 바로 막는다.
- 포기하는 가치: 큰 트리에서는 전체 구조가 실제로 한 화면에 들어오지 않아 `전체 맞춤`이라는 기대와 어긋난다.
- 주요 불확실성: 사용자가 화면 밖에 구조가 더 있다는 사실과 이동 방향을 알 수 있는가?
- 프로토타입 질문: 읽을 수 있는 최소 배율을 적용했을 때 사용자가 전체 범위를 충분히 파악할 수 있는가?

### 후보 B. 조망과 읽기 맞춤을 명시적으로 분리

`전체 구조 보기`는 현재처럼 전체 범위를 보여주고, `읽기 좋은 크기로 보기`는 선택 노드나 현재 영역을 가독 가능한 배율로 맞춘다.

- 기대 효과: 두 동작의 약속이 명확하고 각 목적에 맞는 배율 정책을 가질 수 있다.
- 포기하는 가치: 도구와 개념이 하나 늘어나며, 사용자가 적절한 동작을 골라야 한다.
- 주요 불확실성: 두 동작의 차이를 설명 없이 발견하고 기억할 수 있는가?
- 프로토타입 질문: 사용자가 현재 필요한 보기를 망설이지 않고 선택할 수 있는가?

### 후보 C. 전체 조망에서 관심 영역으로 이어지는 단계적 탐색

전체 구조를 축소해서 보여주는 상태는 유지하되, 노드나 서브트리를 선택하면 그 영역을 읽기 좋은 배율로 자연스럽게 확대한다. 다시 전체 구조로 돌아가는 경로를 함께 제공한다.

- 기대 효과: 전체 위치를 먼저 파악한 뒤 관심 영역으로 들어가는 탐색 흐름이 자연스럽다.
- 포기하는 가치: 조망 상태의 제목은 여전히 읽기 어렵고, 선택과 카메라 이동의 규칙이 복잡해질 수 있다.
- 주요 불확실성: 축소 상태에서도 사용자가 관심 영역을 구별하고 정확히 선택할 수 있는가?
- 프로토타입 질문: 조망 → 선택 → 읽기 → 조망의 왕복 과정에서 위치 감각이 유지되는가?

### 후보 D. 조망 전용 표면을 따로 제공

주 캔버스는 읽을 수 있는 배율을 유지하고, 전체 구조는 미니맵이나 별도의 개요 화면에서 보여준다. 개요에서 영역을 선택하면 주 캔버스가 그 위치로 이동한다.

- 기대 효과: 조망과 읽기가 동시에 존재할 수 있고, 큰 트리에서도 주 캔버스의 가독성을 희생하지 않는다.
- 포기하는 가치: 화면 공간과 구현 복잡도가 가장 많이 늘어나며 작은 화면에서는 별도 대응이 필요하다.
- 주요 불확실성: 사용자가 개요와 본문 사이의 위치 관계를 쉽게 연결할 수 있는가?
- 프로토타입 질문: 별도 개요가 실제 탐색을 돕는가, 아니면 작은 보조 화면만 하나 더 생기는가?

## 후보 비교

아직 사용자 검증 전이므로 평가는 상대적인 초기 예상이다.

| 기준                   | A. 가독성 하한 | B. 동작 분리 | C. 단계적 탐색     | D. 별도 개요 |
| ---------------------- | -------------- | ------------ | ------------------ | ------------ |
| 전체 구조 동시 조망    | 낮음           | 높음         | 높음               | 높음         |
| 제목 가독성 보장       | 높음           | 높음         | 읽기 상태에서 높음 | 높음         |
| 목적의 명확성          | 보통           | 높음         | 보통               | 높음         |
| 위치 감각의 연속성     | 보통           | 보통         | 높음               | 확인 필요    |
| 현재 구조에서의 변경량 | 작음           | 중간         | 중간               | 큼           |
| 큰 트리로의 확장성     | 보통           | 높음         | 높음               | 높음         |

## 후보 선택 제안

첫 프로토타입에서는 다음 세 가지를 비교하는 것이 정보 대비 비용이 적다.

1. **A**를 최소 변경 기준안으로 둔다.
2. **B**로 두 목적을 명시적으로 나눴을 때의 이해도를 본다.
3. **C**로 두 목적을 하나의 탐색 흐름으로 연결했을 때의 자연스러움을 본다.

**D**는 B와 C를 검증한 뒤에도 조망과 읽기를 같은 캔버스에서 해결하기 어렵다는 근거가 생기면 탐색한다. 처음부터 미니맵을 만들면 화면 구조와 상호작용 비용이 커져, 문제보다 해법의 형태에 일찍 고착될 가능성이 있다.

### 다음 결정

다음과 같이 후보를 특정했다.

- **채택 방향: A + B** — 읽기 상태에는 가독성 하한을 적용하고, 전체 구조 보기와 읽기 보기를 명시적으로 분리한다.
- **탐색 트랙: C** — 현재 구현 방향에 바로 합치지는 않지만 조망과 포커스를 오가는 고급 탐색 구조를 프로토타입한다.
- **보류: D** — A+B와 C의 검증 결과로 별도 개요 화면의 필요성이 확인될 때 다시 검토한다.

## 3. 후보 특정

A와 B를 결합한 이유:

- A만 적용하면 `전체 맞춤`이 실제로 전체를 보여주지 못해 동작의 약속이 불분명해진다.
- B로 두 탐색 의도를 분리하면 전체 조망은 기존 배율 정책을 유지하고, 읽기 보기에는 A의 가독성 하한을 적용할 수 있다.
- 사용자는 목적에 맞는 동작을 선택해야 하지만 각 동작이 제공하는 결과는 더 예측 가능해진다.

C를 탐색 트랙으로 남긴 이유:

- 조망 → 관심 영역 선택 → 읽기 → 조망 복귀의 흐름은 큰 트리를 탐색하는 장기적인 UI 구조로 발전할 수 있다.
- breadcrumb, 형제 간 이동, 비관심 영역 흐림, 포커스 경로 강조처럼 다른 기능에도 재사용할 수 있는 상호작용을 발견할 가능성이 있다.
- 반면 자동 카메라 이동과 선택의 결합은 사용자의 위치 감각을 해칠 수 있어 채택 전에 별도 검증이 필요하다.

## 4. 판단용 프로토타입

개발 전용 화면 `/dev/ax-tree-navigation-lab`에서 같은 고밀도 fixture로 두 안을 비교한다.

- A+B: `전체 구조`와 `읽기 보기`를 명시적으로 전환한다. 읽기 보기의 78%는 확정 정책이 아니라 가독성 하한을 체감하기 위한 실험값이다.
- C: 전체 구조에서 가지를 선택하면 해당 가지를 확대하고, breadcrumb·형제 이동·주변 흐림·전체 복귀를 제공한다.
- 제품의 168×60px 노드, 32px 형제 간격, 최저 30% 배율을 그대로 사용한다.
- 노드·연결선·캔버스는 현재 선택된 제품 디자인 테마의 토큰을 사용한다.
- 제품 데이터나 저장 기능에는 연결하지 않는다.

실행 방법과 확인 과제는 [프로토타입 문서](../prototypes/sibling-node-navigation.md)에 분리했다.

## 5. A+B 동작 계약 초안

### 전체 구조

- 현재처럼 보이는 노드 전체를 시각 프레임에 맞춘다.
- 최대 배율은 100%, 최소 배율은 30%다.
- 전체 형태 파악이 목적이며 제목 가독성을 보장하지 않는다.

### 읽기 보기

- 정적인 최소 가독 배율과 읽기 창이 보장해야 할 최소 행·깊이 슬롯 수를 둔다.
- 최소 슬롯 수를 모두 담을 수 있는 범위에서 가능한 가장 큰 배율을 적용한다.
- 계산된 배율이 최소 가독 배율보다 작으면 슬롯 수보다 가독성 하한을 우선하고, 용량 부족 상태로 취급한다.
- 포커스 노드의 왼쪽 위를 읽기 창의 좌측 상단 기준점에 놓는다.
- 기준점은 도구 UI와 노드가 겹치지 않게 최소 패딩을 확보한다.
- 포커스 노드의 오른쪽은 더 깊은 노드, 아래쪽은 다음 형제와 형제 서브트리를 보여준다.
- 기준점의 왼쪽과 위쪽 노드는 화면 밖으로 나가며, 오른쪽과 아래쪽도 읽기 창의 용량을 넘으면 잘린다.
- pan과 zoom은 계속 허용해 잘린 영역으로 이동할 수 있게 한다.
- 선택 노드가 있으면 그 노드를 포커스로 사용한다. 선택 노드가 없을 때의 기준은 제품 구현 전에 추가 결정한다.

프로토타입은 최소 배율 78%, 최대 배율 100%, 최소 용량 `세로 4개 × 깊이 3단계`를 사용한다. 최소 패딩은 위 96px·오른쪽 56px·아래 72px·왼쪽 56px다. 이 값은 최종 디자인 토큰이 아니라 계산과 방향을 확인하기 위한 값이다.

### 읽기 창 용량 계산

노드 크기와 간격이 고정된 현재 가로 전개 방식에서는 먼저 최소 슬롯이 차지하는 크기와 적용 가능한 최대 배율을 계산한다.

```text
사용 가능 너비 = 화면 너비 - 왼쪽 패딩 - 오른쪽 패딩
사용 가능 높이 = 화면 높이 - 위 패딩 - 아래 패딩

최소 슬롯 너비 = 최소 깊이 수 × 노드 너비 + (최소 깊이 수 - 1) × 깊이 간격
최소 슬롯 높이 = 최소 행 수 × 노드 높이 + (최소 행 수 - 1) × 형제 간격

적용 배율 = min(
  최대 배율,
  사용 가능 너비 / 최소 슬롯 너비,
  사용 가능 높이 / 최소 슬롯 높이
)

적용 배율이 최소 배율보다 작으면 최소 배율을 적용한다.

실제 깊이 수 = floor((사용 가능 너비 / 적용 배율 + 깊이 간격) / (노드 너비 + 깊이 간격))
실제 행 수   = floor((사용 가능 높이 / 적용 배율 + 형제 간격) / (노드 높이 + 형제 간격))
```

현재 제품 값은 노드 168×60px, 깊이 간격 64px, 형제 간격 32px다. 계산 결과는 실제 데이터 노드 수가 아니라 **화면에 완전히 들어올 수 있는 최대 논리 슬롯 수**다. 트리가 성기거나 서브트리 형태가 불균일하면 일부 슬롯은 비어 있을 수 있다.

앞쪽 패딩은 포커스 기준점을 안정적으로 유지한다. 논리 슬롯을 채운 뒤 남은 공간은 오른쪽과 아래쪽의 후행 패딩이 되어, 화면 크기가 달라도 마지막으로 완전히 보이는 노드 뒤에 여유가 남는다. 기존 프로토타입보다 패딩을 넓혀 실제 트리가 차지하는 시각 영역과 전체 가용 영역의 경계를 분명하게 했다.

### 위상 좌표와 화면 투영

서비스 로직은 노드 위치를 화면의 x/y보다 먼저 `depth × breadth` 위상 좌표로 다룬다.

- `depth`: 부모에서 자식으로 진행하는 세대 깊이다.
- `breadth`: 같은 깊이에서 형제 전개 방향의 시각적 lane이다. 서버 데이터의 형제 순번이나 픽셀 너비가 아니며, 앞선 형제의 서브트리가 여러 lane을 차지하면 그만큼 건너뛴다.
- 현재 가로 전개에서는 `depth → x`, `breadth → y`로 투영한다. 세로 전개나 역방향 배치는 위상 좌표를 바꾸지 않고 투영 규칙만 교체한다.

읽기 창 계산 결과는 화면 카메라와 함께 다음 위상 창을 반환한다.

```text
TopologyWindow {
  origin: { depth, breadth },
  size: { depth, breadth }
}
```

원점은 포커스 노드이고 끝 경계는 포함하지 않는다. 따라서 노드가 읽기 범위에 들어오는지, 화면 방향이 바뀐 뒤 어느 포커스를 복원할지, 키보드로 어느 축을 이동할지를 픽셀 좌표와 분리해 판단할 수 있다. 위상 좌표와 위상 창은 레이아웃에서 파생되는 UI 상태이며 제품 엔티티에 저장하지 않는다.

### 아직 확정하지 않은 항목

- 78%와 100%를 최종 최소·최대 배율로 사용할지
- 최소 `세로 4개 × 깊이 3단계`가 적절한지
- 넓어진 네 방향 패딩을 고정값으로 둘지 캔버스 크기에 비례하게 만들지
- 선택 노드가 없을 때 현재 viewport 기준점을 사용할지 다른 기본 포커스를 선택할지
- 경계에서 일부만 보이는 다음 노드를 탐색 가능성의 신호로 남길지 완전히 가릴지
- 패널과 플레이어가 열리거나 크기가 바뀔 때 읽기 창을 즉시 다시 계산할지
- 불균일한 노드 크기에서 `breadth` lane을 정수 슬롯으로 유지할지 가변 폭 좌표로 확장할지

이 사례가 진행되면서 확인된 공통 패턴은 [프레임워크 본문](../framework.md)과 [용어 사전](../glossary.md)에 반영한다.
