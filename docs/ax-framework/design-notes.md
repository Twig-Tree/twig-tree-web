# 설계 기록

> 상태: 초안

이 문서는 프레임워크의 본문을 간결하게 유지하면서, 구조를 선택한 이유와 아직 확정하지 않은 질문을 보존한다.

## 현재 채택한 방향

### D-001. 절차보다 불확실성 감소를 중심에 둔다

단계를 순서대로 완료하는 것 자체는 목표가 아니다. 각 단계가 다음 판단에 필요한 불확실성을 줄이지 못한다면 생략하거나 다시 설계한다.

### D-002. 사람의 선택 지점을 명시한다

AI가 탐색과 제작을 넓게 담당할 수 있더라도 제품 방향과 가치의 선택을 암묵적으로 대신하지 않는다. 중요한 선택은 결정 게이트로 드러낸다.

### D-003. 설명보다 판단 가능한 경험을 우선한다

UI와 상호작용 문제는 글만으로 합의하기 어렵다. 가능한 경우 실제 데이터에 가까운 fixture와 비교 가능한 프로토타입을 사용한다.

### D-004. 본문, 용어, 설계 이유, 사례를 분리한다

반복해서 읽는 흐름을 짧게 유지하고, 정의와 배경 설명이 본문을 무겁게 만들지 않도록 분리했다. 각 문서는 독립적으로 이동하거나 합칠 수 있을 정도로 얇게 유지한다.

### D-005. 지금은 문서 단위 변경 용이성을 우선한다

프레임워크의 경계가 안정되지 않았으므로 문장이나 문단에 고정 ID를 부여하지 않는다. 대신 파일의 역할을 나누고 상대 링크만 사용한다. 세밀한 추적이 실제로 필요해지면 문단 식별자나 별도의 변경 기록을 검토한다.

### D-006. 채택하지 않은 후보도 탐색 트랙으로 보존할 수 있다

후보 선택을 채택과 폐기의 이분법으로만 다루면, 현재 문제에는 과하지만 미래 구조에 가치 있는 상호작용을 잃을 수 있다. 다만 탐색 트랙은 제품 범위가 아니므로 확인 질문과 중단 조건을 정하고 프로토타입 수준에서 격리한다.

## 열린 질문

### Q-001. 어느 결정에 사람의 명시적 확인이 필요한가?

모든 단계에 승인을 요구하면 흐름이 느려지고, 너무 적으면 AI가 방향을 암묵적으로 결정한다. 결정의 영향도, 되돌리기 비용, 불확실성을 기준으로 게이트를 구분할 필요가 있다.

### Q-002. 단계별 최소 산출물을 고정할 것인가?

일관된 형식은 인수인계를 돕지만 작은 작업에도 불필요한 문서를 만들 수 있다. 사례가 쌓이기 전까지는 결과물의 종류보다 답해야 할 질문만 제시한다.

### Q-003. 문단 단위 변경 추적이 필요한가?

현재는 Git 이력과 문서 단위 분리로 충분하다고 가정한다. 여러 팀이 동시에 프레임워크 일부를 참조하거나 자동화가 문단을 직접 소비하게 되면 다시 검토한다.

### Q-004. 구현 완료와 검증 완료를 어디까지 분리할 것인가?

팀 내부 확인, 실제 사용자 확인, 지표 관찰은 비용과 시간이 다르다. 작업 유형에 따른 검증 수준을 추후 정의할 필요가 있다.

## 문서 개선 규칙

- 실제 사례에서 같은 문제가 두 번 이상 나타나면 공통 개념 또는 규칙으로 승격을 검토한다.
- 사용되지 않는 단계나 산출물은 유지 이유가 없으면 제거한다.
- 용어의 의미가 바뀌면 용어 사전을 먼저 고치고 관련 문서를 갱신한다.
- 중요한 구조 변경에는 이 문서에 결정 항목 또는 열린 질문을 추가한다.
