# AX Framework 흐름

> 상태: 초안 0.1

## 목적

요구사항이 불확실한 상황에서 AI와 작업자가 곧바로 하나의 해법에 고착되지 않도록 한다. 각 단계는 모호함을 조금씩 줄이고, 사람이 판단해야 할 시점과 판단에 필요한 결과물을 분명하게 만드는 데 목적이 있다.

## 기본 흐름

```text
피드백
  ↓
문제 정제
  ↓
후보 탐색
  ↓
방향 선택
  ↓
판단용 프로토타입
  ↓
결정 · 구현 · 전달
  ↓
검증과 반복
```

앞 단계로 돌아가는 것은 실패가 아니다. 새로 확인한 사실 때문에 문제 정의나 후보가 달라졌다면 가장 가까운 단계로 돌아간다.

## 1. 문제 정제

사용자의 표현을 바로 구현 항목으로 번역하지 않고, 관찰된 현상과 아직 확인하지 못한 해석을 분리한다.

최소 결과물:

- 사용자가 겪은 현상
- 현상이 나타나는 조건
- 영향을 받는 사용자 행동
- 사실, 가설, 열린 질문의 구분

다음 단계로 넘어가는 기준은 문제를 완벽히 이해하는 것이 아니라, **서로 다른 해법을 탐색할 만큼 문제의 경계가 보이는가**이다.

## 2. 후보 탐색

표현만 다른 유사안이 아니라 문제를 푸는 방식이 다른 소수의 후보를 만든다.

각 후보에는 다음만 간략히 붙인다.

- 해결하려는 핵심
- 기대 효과
- 주요 부작용 또는 포기하는 가치
- 확인해야 할 불확실성

후보 수는 고정하지 않는다. 차이가 명확하지 않은 후보를 수만 늘려 제시하지 않는다.

## 3. 방향 선택

작업자가 한 후보를 고르거나 여러 후보의 일부를 조합한다. 선택하지 못했다면 정보가 부족한 지점을 특정하고, 그 판단에 필요한 비교물만 만든다.

이 단계의 핵심은 AI가 결론을 대신 내리는 것이 아니라, 사람이 **무엇을 왜 선택하는지** 분명하게 만드는 것이다.

후보를 반드시 채택과 폐기로만 나눌 필요는 없다.

- **채택 방향**: 현재 문제 해결을 위해 구체화할 후보
- **비교 기준안**: 채택 방향의 효과를 판단하기 위해 함께 만들 최소 후보
- **탐색 트랙**: 당장 구현하지 않더라도 미래 상호작용이나 구조를 발견할 가치가 있어 제한된 프로토타입으로 남길 후보

탐색 트랙에는 확인할 질문과 중단 조건을 붙여, 흥미롭다는 이유만으로 구현 범위가 계속 커지지 않게 한다.

## 4. 판단용 프로토타입

사람이 설명을 읽고 결과를 상상하게 두지 않는다. 선택에 필요한 차이를 직접 경험하거나 비교할 수 있는 가장 작은 결과물을 만든다.

프로토타입은 목적에 따라 달라질 수 있다.

- 전후 화면 비교
- 상호작용 가능한 개발용 화면
- 대표 데이터와 경계 데이터 fixture
- 짧은 영상 또는 이미지
- 동작 규칙을 보여주는 테스트

완성도보다 **결정에 필요한 질문에 답할 수 있는가**를 기준으로 한다.

## 5. 결정 · 구현 · 전달

선택한 방향과 선택 이유, 의도적으로 제외한 범위를 짧게 기록한 뒤 제품에 구현한다.

팀이 확인할 수 있는 결과물에는 가능하면 다음이 포함된다.

- 변경 전후의 차이
- 실행하거나 접근하는 방법
- 대표 시나리오와 경계 조건
- 아직 남은 제약 또는 후속 질문

코드만 존재하고 팀이 결과를 쉽게 확인할 수 없다면 전달이 끝난 것으로 보지 않는다.

## 6. 검증과 반복

최초 피드백에서 드러난 문제가 실제로 줄었는지 확인한다. 새 피드백은 구현 수정으로 바로 보내지 않고, 문제 정의가 바뀐 것인지 구현 품질의 문제인지 먼저 구분한다.

반복 경로의 예:

- 구현이 결정과 다름 → 구현으로 돌아간다.
- 프로토타입에서 놓친 사용 조건이 있음 → 프로토타입으로 돌아간다.
- 선택한 해법의 부작용이 큼 → 후보 탐색으로 돌아간다.
- 최초 해석이 틀림 → 문제 정제로 돌아간다.

## 전 과정의 공통 원칙

- 모르는 것을 아는 것처럼 채우지 않는다.
- 사람의 결정이 필요한 지점을 숨기지 않는다.
- 산출물은 문서의 완성도가 아니라 다음 판단에 기여하는 정도로 평가한다.
- 되돌리기 어려운 결정일수록 더 이른 시점에 비교하고 확인한다.
- 프레임워크 자체도 사례를 통해 검증한다.
