# GitHub PR

@.github/PULL_REQUEST_TEMPLATE.md

PR 생성도 공개로 게시되는 행동이라 **사용자의 명시적인 확인 없이는 절대 push나 `gh pr create`를 실행하지 않는다.** 초안을 보여주는 것과 실제로 올리는 것은 항상 분리된 단계다.

## 컨텍스트 수집

1. `git status`로 미커밋 변경이 있는지 확인한다. 있으면 먼저 사용자에게 알리고, 커밋할지 확인한다 — 이 skill은 커밋 여부까지 임의로 판단하지 않는다.
2. base 브랜치(보통 `main`) 대비 현재 브랜치가 몇 커밋 앞서 있는지, 원격에 push된 상태인지 확인한다.
3. `git log <base>..HEAD`와 `git diff <base>...HEAD`로 이번 PR에 들어갈 커밋과 변경 내용 전체를 파악한다 — 마지막 커밋만 보지 않는다.
4. 관련 이슈 번호를 찾는다: 브랜치 이름, 커밋 메시지, 대화 맥락에 이슈 번호가 있는지 먼저 보고, 없으면 `gh issue list`에서 관련 있어 보이는 이슈를 찾아 사용자에게 맞는지 확인한다. 끝까지 못 찾으면 추측해서 채우지 말고 사용자에게 물어본다.

## 템플릿 채우기

위에서 import한 템플릿 구조를 그대로 따라 작성한다.

- `## 🚀 관련 이슈`: `close #<issue_number>` — 이슈 번호가 확정된 경우에만 적는다. 확정 못 했으면 이 섹션을 비워두고 사용자에게 알린다.
- `## ✏️ 요약`: 이번 PR이 무엇을 하는 변경인지 한두 문장.
- `## ✅ 작업 내용`: 커밋/diff를 근거로 한 실제 변경사항을 항목별로 나열한다. 커밋 메시지를 그대로 복사하지 말고 리뷰어가 이해하기 쉽게 정리한다.
- `## 🧪 테스트 방법`: 실제로 실행/확인한 방법이 있으면 그걸 적는다. 확인 안 한 부분은 "확인 못 함"이라고 솔직히 적는다 — 안 해본 검증을 한 것처럼 쓰지 않는다.
- `## 📷 참고 자료`: 스크린샷/링크가 없으면 비워둔다. 임의로 만들어내지 않는다.
- `## ☝️ 논의 사항`: 리뷰어가 판단해야 할 트레이드오프나 애매한 결정이 있으면 적고, 없으면 비워둔다.

## 확인 요청

PR 제목과 본문 전체(위 템플릿 채운 결과)를 사용자에게 보여주고, 이대로 올릴지 물어본다. base 브랜치, 현재 브랜치가 push됐는지 여부도 함께 알린다. 명확한 승인이 있을 때만 다음 단계로 진행한다.

## 실제 생성 (승인 후에만)

1. 브랜치가 원격에 없거나 뒤처져 있으면 push한다 (`git push -u origin <branch>`) — 이 역시 승인 범위 안의 행동이므로 별도로 다시 묻지 않는다.
2. 본문을 임시 파일에 써서 `gh pr create --title "<title>" --body-file <tmpfile>` 로 생성한다.
3. 생성된 PR URL을 사용자에게 보여준다.
