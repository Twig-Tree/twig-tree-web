# Twigtree AI 강의 웹 플레이어 프론트엔드 데모 구현

## 1. 작업 목표

현재 프로젝트 Twigtree에 AI 강의 웹 플레이어 데모를 구현한다.

이번 작업의 목적은 백엔드 API나 실제 AI 서비스를 연동하는 것이 아니라, **목데이터만으로 AI 강의가 재생되는 사용자 경험과 인터랙션을 검증하는 것**이다.

현재는 프론트엔드만 구현하며, 서버 및 데이터베이스 구현은 추후 진행할 예정이다.

따라서 기존 프로젝트의 트리 화면과 데이터를 최대한 재사용하고, 목데이터를 기반으로 다음 기능이 실제로 동작하는 데모를 만든다.

1. 강의 시작 및 일시정지
2. 강의 음성 재생
3. 음성 재생 시간에 따른 자막 표시
4. 현재 설명하는 트리 노드 강조
5. 관련 노드로 부드럽게 카메라 이동
6. 다음 강의 구간으로 진행
7. 강의 종료 상태 표시

이번 작업에서는 실제 AI 강의 대본 생성, TTS API 호출, 서버 저장 및 MP4 생성 기능을 구현하지 않는다.

## 2. 구현 전 필수 작업: 기존 코드 분석

코드를 수정하기 전에 현재 프론트엔드 저장소를 먼저 분석한다.

특히 다음 항목을 확인한다.

- Next.js 및 React 버전과 프로젝트 구조
- TypeScript 설정 및 경로 별칭
- 현재 사용 중인 React Flow 라이브러리와 버전
- 트리 화면의 진입 페이지 및 관련 컴포넌트
- 노드와 엣지의 데이터 타입 및 ID 체계
- 노드 좌표와 뷰포트를 제어하는 기존 방식
- 상태 관리 라이브러리와 상태 관리 패턴
- 스타일링 방식, 디자인 토큰 및 공통 UI 컴포넌트
- 기존 모달, 버튼, 툴팁, 아이콘 및 로딩 UI
- 기존 폴더 구조, 파일명 규칙, import 순서 및 네이밍 컨벤션
- ESLint, Prettier 등 코드 검사 설정
- 테스트 코드와 테스트 작성 규칙

분석 결과를 바탕으로 기존 코딩 스타일과 구조를 따르며 구현한다.

**중요: 기존 프로젝트의 코드 스타일을 임의로 바꾸거나 새로운 컨벤션을 도입하지 않는다.**

## 3. 코딩 규칙

다음 규칙을 반드시 지킨다.

### 3.1. 기존 코드 스타일 준수

- 기존 컴포넌트의 작성 방식과 폴더 구조를 따른다.
- 기존 프로젝트의 TypeScript 타입 정의 방식을 따른다.
- 기존 상태 관리 패턴을 따른다.
- 기존 스타일링 기술과 디자인 토큰을 사용한다.
- 기존 공통 컴포넌트가 있다면 우선 재사용한다.
- 기존 아이콘 라이브러리가 있다면 그대로 사용한다.
- 기존 코드와 일관된 네이밍 및 파일 분리 방식을 유지한다.
- 불필요한 라이브러리를 새로 설치하지 않는다.
- 기존 컴포넌트나 공통 로직을 중복 구현하지 않는다.

### 3.2. 변경 범위 최소화

- 기존 트리 편집 기능을 훼손하지 않는다.
- 강의 플레이어는 기존 트리 화면에 자연스럽게 통합한다.
- 강의 데모와 관계없는 기존 코드는 수정하지 않는다.
- 기존 API 호출이나 상태 관리 로직을 불필요하게 변경하지 않는다.
- 실제 구현 전에 관련 코드의 사용처와 의존 관계를 확인한다.
- 기존 프로젝트에 적합한 구현 방법이 있다면 새로운 구조보다 기존 구조를 우선한다.

### 3.3. 코드 품질

- `any` 타입을 무분별하게 사용하지 않는다.
- 컴포넌트의 책임을 명확하게 분리한다.
- 중복된 상태를 불필요하게 만들지 않는다.
- 타이머, 이벤트 리스너 및 재생 관련 리소스를 적절히 정리한다.
- React의 렌더링 및 생명주기 특성을 고려한다.
- 비동기 동작과 재생 상태 변경 시 발생할 수 있는 경쟁 상태를 고려한다.
- 사용자가 반복해서 재생하거나 일시정지해도 상태가 꼬이지 않도록 한다.
- 기존 코드베이스의 lint 및 타입 검사 규칙을 통과하도록 작성한다.

## 4. 구현할 사용자 경험

### 4.1. 강의 플레이어 진입

기존 트리 화면에 강의 시작 버튼을 추가하거나, 현재 프로젝트의 UI 구조에 맞는 진입 방식을 선택한다.

버튼을 누르면 강의 플레이어가 시작된다.

기존 화면 구조와 디자인을 먼저 확인한 후, 사이드 패널, 별도 페이지 또는 기존 화면 내 플레이어 중 가장 자연스러운 방식을 선택한다.

기존 트리 편집 경험과 충돌하지 않도록 한다.

### 4.2. 강의 재생

강의 재생은 다음 순서로 동작한다.

1. 강의 시작 버튼을 누른다.
2. 첫 번째 강의 구간에 연결된 노드로 카메라가 이동한다.
3. 해당 구간의 음성이 재생된다.
4. 음성 재생 시간에 맞춰 자막이 표시된다.
5. 현재 설명하는 노드가 강조된다.
6. 다음 구간이 시작되면 자막, 노드 강조 및 카메라 위치가 갱신된다.
7. 마지막 구간이 끝나면 강의 완료 상태를 표시한다.

이 모든 동작은 서버 없이 프론트엔드의 목데이터만으로 확인할 수 있어야 한다.

### 4.3. 음성 재생

이번 데모에서는 실제 TTS API를 호출하지 않는다.

가능한 구현 방법을 기존 프로젝트 상황에 맞춰 검토한다.

우선순위는 다음과 같다.

1. 프로젝트에 사용할 수 있는 음성 파일이나 기존 에셋이 있다면 활용한다.
2. 적절한 음성 파일이 없다면, 브라우저의 `SpeechSynthesis` API를 이용해 목데이터의 강의 대본을 음성으로 재생하는 방식을 검토한다.
3. 브라우저 음성 합성을 사용하기 어렵거나 기존 구조와 맞지 않는다면, 재생 시간을 시뮬레이션하는 대안을 제시한다.

음성 재생을 구현할 경우 실제 재생 상태와 자막 및 노드 강조 상태가 일치하도록 한다.

`SpeechSynthesis`를 사용하는 경우 브라우저별 한국어 음성 지원 차이를 고려한다. 음성 합성이 지원되지 않거나 사용할 수 없는 환경에서도 데모를 확인할 수 있는 대체 동작을 제공한다.

음성이 실제로 재생되지 않는 환경에서 음성이 재생되는 것처럼 사용자에게 오해를 주지 않는다.

### 4.4. 자막

- 현재 재생 중인 문장을 자막 영역에 표시한다.
- 초기 버전에서는 문장 단위 자막을 지원한다.
- 목데이터의 재생 구간 정보에 따라 자막이 변경되어야 한다.
- 일시정지하면 자막도 해당 상태를 유지한다.
- 다시 재생하면 이어서 진행한다.
- 다음 구간으로 이동하면 해당 구간의 자막을 표시한다.

실제 음성 파일이 있는 경우에는 음성의 재생 시간을 기준으로 자막을 동기화한다.

브라우저 음성 합성을 사용하는 경우에는 문장별 음성 재생 이벤트를 활용할 수 있는지 확인한다. 정확한 음성 타임스탬프를 확보할 수 없다면 데모에 적합한 현실적인 동기화 방식을 선택하고 그 한계를 명시한다.

### 4.5. 노드 강조

- 현재 강의 구간에 대응되는 노드를 강조한다.
- 기존 노드 스타일과 충돌하지 않도록 한다.
- 현재 노드와 일반 노드가 명확히 구별되어야 한다.
- 다음 구간으로 이동하면 강조 대상이 갱신된다.
- 강의가 끝나면 현재 노드 강조를 해제하거나 완료 상태로 표시한다.

강의 플레이어의 상태가 기존 트리 데이터 자체를 불필요하게 변경하지 않도록 한다.

### 4.6. 카메라 이동

React Flow의 기존 버전과 사용 방식을 확인하고 적합한 뷰포트 제어 API를 사용한다.

요구사항은 다음과 같다.

- 현재 설명할 노드가 화면에서 잘 보이도록 이동한다.
- 이동이 즉시 일어나지 않고 부드럽게 진행된다.
- 필요하면 관련 노드들이 함께 보이도록 확대 비율과 화면 영역을 조정한다.
- 다음 구간이 시작되면 다음 대상 노드로 이동한다.
- 노드 좌표가 준비되지 않은 상황을 처리한다.
- 트리 편집 및 드래그 기능과 충돌하지 않는다.

카메라 이동은 미리 만들어진 영상이 아니라, 웹 화면에서 실행되는 애니메이션으로 구현한다.

## 5. 목데이터 설계

실제 API가 없어도 강의의 전체 동작을 검증할 수 있도록 타입이 정의된 목데이터를 작성한다.

기존 프로젝트에 노드 및 엣지 타입이 있다면 재사용한다.

강의 구간은 개념 노드와 연결되어야 한다. 예시는 다음과 같다.

```ts
interface MockLectureSegment {
  id: string;
  nodeId: string;
  script: string;
  subtitles: Array<{
    start: number;
    end: number;
    text: string;
  }>;
  camera: {
    targetNodeIds: string[];
    zoom: number;
    durationMs: number;
  };
}
```

위 타입은 개념 예시다. 실제 프로젝트의 타입 정의 방식과 네이밍 규칙에 맞춰 조정한다.

목데이터는 다음 조건을 충족해야 한다.

- 최소 3개의 강의 구간을 포함한다.
- 각 구간이 실제 트리 노드 ID와 연결된다.
- 강의 구간별 대본이 존재한다.
- 자막이 문장 단위로 구분된다.
- 카메라 이동 대상 노드가 존재한다.
- 노드 강조와 카메라 이동이 실제 트리에서 확인 가능하다.
- 재생, 일시정지, 다음 구간 이동 및 종료 상태를 검증할 수 있다.

기존 트리 데이터를 확인하기 전에 노드 ID를 임의로 가정하여 연결하지 않는다.

## 6. 재생 상태 관리

현재 프로젝트의 상태 관리 방식을 따르며, 강의 플레이어에 필요한 최소 상태를 설계한다.

필요한 상태의 예시는 다음과 같다.

- 강의 재생 상태
- 현재 강의 구간 인덱스
- 현재 자막 인덱스
- 현재 재생 위치 또는 진행 상태
- 강의 완료 여부

음성 재생 상태, 자막 상태, 노드 강조 상태 및 카메라 이동 상태가 서로 어긋나지 않도록 한다.

가능하면 현재 강의 구간과 재생 위치를 기준으로 화면 상태를 파생한다.

재생 및 일시정지 시 다음 사항을 확인한다.

- 음성이 중복 재생되지 않는가?
- 일시정지 후 다시 재생할 수 있는가?
- 다음 구간으로 이동하면 이전 음성이 중단되는가?
- 컴포넌트가 언마운트될 때 음성 재생과 타이머가 정리되는가?
- 빠르게 버튼을 여러 번 눌러도 상태가 꼬이지 않는가?
- 강의 완료 후 처음부터 다시 재생할 수 있는가?

## 7. UI/UX 원칙

기존 Twigtree의 디자인 시스템과 UI 스타일을 최우선으로 한다.

- 기존 디자인 토큰과 공통 컴포넌트를 활용한다.
- 별도의 디자인 시스템을 새로 만들지 않는다.
- 기존 트리 화면과 자연스럽게 어울리도록 한다.
- 강의 재생 상태를 사용자가 명확하게 파악할 수 있어야 한다.
- 자막은 읽기 쉬워야 한다.
- 재생 및 일시정지 버튼은 명확하게 구분한다.
- 카메라 이동과 노드 강조는 학습에 도움이 되도록 절제해서 사용한다.
- 과도한 애니메이션이나 불필요한 장식은 피한다.
- 기존 반응형 레이아웃 규칙을 따른다.

## 8. 이번 작업의 범위에서 제외할 사항

다음 기능은 이번 작업에서 구현하지 않는다.

- Spring Boot 백엔드 API 추가
- PostgreSQL 스키마 변경
- Redis 연동
- 실제 LLM API를 통한 강의 대본 생성
- 실제 TTS API 연동
- 강의 콘텐츠의 서버 저장
- 사용자별 강의 이력 저장
- MP4 파일 생성 및 내보내기
- 강사 아바타 생성
- 강의 생성 작업 큐 및 서버 측 비동기 처리

다만 향후 서버 연동을 고려하여 목데이터와 실제 데이터의 교체가 지나치게 어려워지지 않도록 구조를 설계한다.

이번 단계에서 API 추상화나 서비스 계층을 과도하게 만들지는 않는다.

## 9. 완료 기준

다음 조건을 충족하면 작업 완료로 판단한다.

1. 기존 트리 화면에서 강의 데모를 실행할 수 있다.
2. 목데이터만으로 전체 강의 흐름을 확인할 수 있다.
3. 강의 구간에 맞춰 카메라가 부드럽게 이동한다.
4. 현재 설명 중인 노드가 강조된다.
5. 자막이 재생 구간에 맞춰 변경된다.
6. 음성 재생 또는 명시적인 대체 재생 방식이 동작한다.
7. 일시정지, 재개, 다음 구간 이동 및 강의 종료가 동작한다.
8. 기존 트리 편집 기능이 정상적으로 유지된다.
9. TypeScript 타입 검사 및 프로젝트의 관련 lint 검사를 수행한다.
10. 기존 테스트가 있다면 관련 테스트를 실행하고 결과를 확인한다.
11. 변경 사항이 기존 코드 스타일 및 컨벤션을 따른다.

검사를 실행할 수 없다면 실행하지 못한 이유를 명시한다. 검사 결과를 확인하지 않고 통과했다고 보고하지 않는다.
